# 🤝 Contributing to the Software Engineering Playbook

> **Start here if you want to suggest an improvement or report a problem.**

---

## Our Issue-First Philosophy

This playbook is **maintainer-curated**. That is a deliberate choice.

The repository's value comes from its coherent teaching voice, progressive structure, and carefully sequenced learning path — from fundamentals to advanced patterns. Every topic is placed where it is for a reason, and explanations are written to build on each other.

**For this reason, content contributions (new sections, rewritten explanations, structural changes) are not accepted as pull requests.** Instead, we ask you to open an issue so we can discuss the change together before any integration work happens.

This does not mean your input is unwelcome. It means we protect the learning experience for everyone — including you, when you revisit a topic later.

---

## Why We Use Structured Issue Templates

Every issue template is designed to capture the minimum information needed to evaluate a suggestion:

| Template | When to Use |
|----------|-------------|
| **[Bug Report](./.github/ISSUE_TEMPLATE/bug_report.md)** | Code snippets that don't work, contradictory explanations, or missing steps |
| **[Documentation Problem](./.github/ISSUE_TEMPLATE/documentation_problem.md)** | Outdated information, factual errors, or confusing wording |
| **[Topic Suggestion](./.github/ISSUE_TEMPLATE/topic_suggestion.md)** | A new topic or learning level you think is missing |
| **[General Feedback](./.github/ISSUE_TEMPLATE/general_feedback.md)** | Questions, perspectives, or open-ended ideas |

Using the right template ensures your feedback reaches the right context and gets the attention it deserves.

---

## What Is Welcome Without an Issue

Not everything requires a discussion. The following are perfectly fine to submit as pull requests:

- **Typo corrections**
- **Broken links**
- **Formatting inconsistencies** (heading levels, list styles, code block formatting)
- **Minor repository maintenance** (missing assets, stale configuration files)

If you are unsure whether something needs an issue first, open an issue anyway. We would rather discuss the idea than merge something that conflicts with the playbook's structure.

---

## What Happens After You Open an Issue

1. A maintainer will label the issue with `status:needs-review`.
2. The issue will be evaluated for alignment with the playbook's teaching goals and structural integrity.
3. If approved, the maintainer will either implement the change directly or open a discussion about the best approach.
4. You are welcome to follow along and participate in the discussion.

---

## The Goal

A playbook that is **easy to navigate**, **consistent in voice**, and **progressive in structure** — so every learner can trust that the path is worth following.

Your feedback is what keeps this repository alive. Thank you for helping us keep it that way.
